# 巡到位项目设计

日期：2026-10-27。阶段：00 工程准备。本文中的“目标设计”不表示已实现。

## 依据与当前事实

业务依据为《03_B02_案例书.md》V0.8R1；实施顺序与字段依据为《04_B02_学生实践指南.md》V0.8R1；《02_巡检改造方案.md》限定参赛版为 Web 单端、二维展示。原资料保存在 D:\分布式设施巡检与复核\_发学生_B02巡检包。

当前采用 Day 1 骨架：Python/FastAPI、SQLite、原生 HTML/CSS/JavaScript。任务 00 只验证启动、页面、现有 API 和运行摘要持久化。GreenMate 只提供可核对的技术参考，不决定新业务。

## 目标与角色

设施管理员查看覆盖与阻塞；巡检人员提交现场记录及复核证据；区域管理员提供访问条件和协同信息。系统回答本轮是否巡到、异常是否确认、证据能否追溯、剩余资源可支持哪些补检方案。

T1：关键设施巡检覆盖；T2：异常项复核与确认；T3：可靠留存与汇聚；T4：现场复核与补证；T5：分析与复盘。T2 成立可以表示已确认存在故障，不等于全部正常。

## 目标架构与边界

Web 四视图 → FastAPI 接口 → 确定性规则服务与 SQLite；天气、RAG、ML、工具调用、LLM 作为可降级的辅助层。四视图为任务总览、设施覆盖与阻塞、证据与现场复核、方案与运行对比。

保留 backend/frontend 目录，随阶段按职责拆分；不提前创建空模块，不引入新前端框架、自动派单、复杂路径优化或专业安全判定。阶段 01 接入 MQTT 与 WebSocket；阶段 05 的复核入口落在 Web。

## 固定业务契约

- 三区域八点位；必检 C01、C02、C04、C05、C07、C08，普通 C03、C06。
- 覆盖依照 inspection_round_id、本轮窗口、来源可追溯的有效现场记录计算；远程在线和告警不能替代现场覆盖；较新远程记录不抹掉仍有效的现场记录。
- 任务四态 established / blocked / pending_verification / unknown 与设施、证据、运行、方案、复核请求状态分开。
- 缺失记录而没有明确未执行事实，不能一概判受阻；接口获取失败不能写成设施 FAULT。
- run_id 代表一次判断，关联输入快照、证据引用、依赖检查、任务和方案结果；完成运行不可覆盖，新证据进入新运行。
- reality 与 what_if 分离，推演记录 parent_run_id 和 assumptions；推演不得修改现实或自动完成补检。
- review_request 关联触发运行、任务、设施、区域及新证据；完成、超时、取消是请求过程状态，需要重新判断任务。
- AI 只解释结构化结果；AI 不可用不抹掉基础判断。照片摘要也是辅助材料，不能自动认定已巡检。

## 数据与接口的阶段职责

阶段 02 建立 facility_observations、inspection_records、evidence；阶段 03 建立任务/依赖定义、runs、run_evidence、dependency_checks、task_results；阶段 04 加入方案与阻塞；阶段 05 加入 review_requests。时间字段分别记录观察、巡检、取得、创建和完成时刻。

阶段 01 引入 GET /health、设施当前状态及 /ws/facilities；阶段 02 引入历史、巡检记录和证据接口；阶段 03 引入运行详情和任务；阶段 04 引入方案；阶段 05 引入复核及补证接口。具体字段沿用指南附录 B/F，按使用阶段实现，不提前替换骨架 API。

## 采用方案的理由

在现有骨架上渐进实施，能保留可核对的起点，并按案例顺序验证；整库复制 GreenMate 会混入番茄状态与模型依赖，从零重搭则重复已有基础工作。此处是工程决策，不是效果或效率的实测结论。
